Full-stack audit of the Unreal MCP toolchain: C++ bridge plugin, Python MCP server, launch/lifecycle tooling, crash history, tool-surface gaps, and workflow opportunities. Goal: a faster, more reliable UE development loop — for Speakeasy3D now, and as a portable toolkit for freelance set-design / virtual-art-department work.

**Method:** two deep source audits (C++ bridge; Python server), live verification against a running editor (token debug enabled), forensic sweep of all 157 editor crash dumps since April, the Notion "Unreal MCP" tracker, and session history. Findings are tagged **[LIVE]** (reproduced today), **[CODE]** (root-caused at file:line), or **[HIST]** (from crash dumps / tracker).

## 0. Executive summary

1. **The MCP is not the instability driver — the environment is.** Of 157 editor crashes since April, only **3** were MCP-caused (2× `set_actor_property`, fixed in `faf784a`; 1× boot-time `load_level`). The dominant tax is **boot-time failures: ~68 crashes (~43%)** from CEF/`libcef.so` (×30), a CDO-creation fatal during plugin mount (×24, MetaXR content implicated), and MetaXR's own `OculusXRHMD_StressTester.cpp:29` assert (×14). At ~8 min per reload that's **9+ hours lost**, and every one looks like "the editor randomly died."
2. **The MCP has two critical latent bugs** found and root-caused this audit: **double execution of mutating commands** (client retries after a response timeout while the server is still executing — no request-id dedup; timeouts are inverted: client 30s vs server 120s) and **no editor-readiness gate** (commands accepted during boot → the TickTaskManager crash we hit). Neither had bitten us visibly yet except the boot crash — both will.
3. **Several everyday tools are quietly broken or wasteful:** `find_assets` returns 0 unless you also pass a class/path **[LIVE+CODE]**; `save_all` reports success even when packages fail to save **[CODE]**; `take_screenshot` can capture a stale frame (no redraw flush) **[LIVE+CODE]**; `get_world_info` costs ~1,776 tokens per call with no filters **[LIVE]**; actor resolution is inconsistent across commands (3 param spellings; some label-aware, some name-only; 3 commands read the wrong world during PIE) **[CODE]**.
4. **The portability story is 80% built but the installer produces a different setup than the one that works.** `install.sh` pip-installs from PyPI and writes a bare `unrealmcp` command; the working setup is a local venv + editable install + absolute path — and port discovery is CWD-relative, so the whole thing only works when the client happens to start in the project root.
5. **Highest-leverage feature gaps** for both Speakeasy and set-design/VAD work: PIE control (play/stop/screenshot-in-play), Sequencer/Movie Render Queue automation (turntables, shot renders, marketing capture), a viewport-framing tool, console-command tool, texture import options, and a crash-aware error surface ("editor crashed: <assertion> — see <dir>" instead of "Failed after 4 attempts").

## 1. Architecture (how a call flows)

```
Claude Code ──stdio──> unrealmcp (Python, FastMCP, 293 tools)
                         │  resolves port: $UNREAL_MCP_PORT → ./Saved/UnrealMCP/port.txt → 55557
                         │  one shared TCP socket, RLock, 4-byte length-prefix JSON framing
                         ▼
              UEpicUnrealMCPBridge (C++ EditorSubsystem, FRunnable accept loop, 1 client at a time)
                         │  AsyncTask(GameThread) per command, socket thread blocks on TFuture (120s)
                         │  GIsRunningUnattendedScript suppresses modals during commands
                         ▼
              9 handler families (Editor/Asset/Blueprint/Graph/Material/DataTable/DataAsset/Widget/Input)
              + execute_python escape hatch (PythonScriptPlugin, base64-wrapped, captures `result`)
```

- **C++ bridge:** ~27k LOC, 0 TODOs, portability-clean (no project hardcoding; port configurable via `DefaultEngine.ini [UnrealMCP]`). Local fork is 7 commits ahead of upstream (`aadeshrao123/Unreal-MCP`), including the crash-safe `set_actor_property` (`faf784a`), `-NoMCP` gating (`6c6d294`), `rename_widget` DisplayLabel fix (`d730c2b`), and the overnight robustness pass (`d2a4f71`).
- **Python server:** pip package `unrealmcp` (venv at `Plugins/UnrealMCP/.venv`, registered in `.mcp.json`). 293 hand-written `@mcp.tool()` wrappers across 15 modules (niagara 97, materials 37, statetree 33, blueprint_graph 22, input 21, assets 16, editor 15, …). All schemas advertised eagerly; no allowlist mechanism.
- **Also in the repo:** a Go CLI (`cli/`) whose port discovery is *correct* (walks up to `.uproject`), a raw-TCP validation suite (`scripts/validate_bridge.py`, 24 checks, hardcoded to this machine), CI (ruff + import smoke only), `install.sh`/`install.bat`, README (claims 280 tools; actual 293).
- **Lifecycle:** `launch-editor.sh` (project repo) — now single-instance with stale-port cleanup.

## 3. MCP findings — critical & high (do these)

### 3.1 Double execution of mutating commands **[CODE, both sides]**
- Client: `unrealmcp/_tcp_bridge.py:195-209` retries all 4 attempts on `TimeoutError`/`socket.error` — *including after `sendall` succeeded* (recv-phase timeout). 
- Server: `EpicUnrealMCPBridge.cpp:835` waits 120s on the game-thread future and **keeps executing after the client gave up**; timeouts are inverted (client 30s < server 120s). `LARGE_OPERATION_COMMANDS` (`_tcp_bridge.py:39-49`) lists only 9 commands — missing `execute_python`, `save_all`, `import_asset`, `compile_*`, screenshots. 
- No request-id/dedup anywhere → a slow `spawn_actor`/`import_asset`/`save_all` can run 2-4×. 
**Fix:** (a) client: only retry failures that occur *before* send completes; (b) flip the timeout hierarchy (client recv > server deadline) and expose per-call timeout; (c) optionally add request-id + last-N response cache server-side for true replay safety.

### 3.2 No editor-readiness gate **[CODE + HIST]**
`StartServer()` runs from `Initialize()` (`EpicUnrealMCPBridge.cpp:100`) and accepts commands during boot; nothing checks world/tick/asset-registry readiness. This is exactly the `!LevelList.Contains(TickTaskLevel)` crash (2026-06-30) and also explains empty `find_assets` results during registry scan. 
**Fix:** gate the game-thread lambda on `GEditor && World && !AssetRegistry.IsLoadingAssets()` → retryable "editor warming up" error; defer port-file write/accept until `OnFEngineLoopInitComplete`.

### 3.3 `find_assets` broken with `name_pattern` only **[LIVE + CODE]**
`EpicUnrealMCPAssetCommands.cpp:216-236`: candidates are only gathered when `class_type` or `path` is supplied; name-only → empty set → `count: 0` (reproduced live: `M_SpaceSky`, `*SpaceSky*`, `SpaceSky` all 0 while `list_assets` shows 3 matches). Matching is case-insensitive **substring**, not glob — a literal `*` can never match. 
**Fix:** registry-wide query when only `name_pattern` given; document substring semantics (or add glob).

### 3.4 `save_all` lies about success **[CODE]**
`EpicUnrealMCPAssetCommands.cpp:736-739` discards `SaveDirtyPackages()`'s return and hardcodes `success: true` — failed/skipped packages (e.g. a BP that won't compile) are reported as saved. Silent data-loss class. 
**Fix:** use the `OutFailedPackages` overload; return the failed list.

### 3.5 Crash-blind, guidance-free error surface **[LIVE experience + CODE]**
On bridge-down the client says only `Failed after 4 attempts: Cannot connect…`. Zero checks of `Saved/Crashes/` (grep: no hits) or port-file presence. We diagnosed every crash by hand this month. 
**Fix (Python):** on connect failure branch: no `port.txt` → "editor not running — `./launch-editor.sh`"; port file present but dead + fresh crash dir → "editor crashed: `<assertion line>` — see `<crash dir>`". Turns the worst recurring failure into a self-explaining one.

### 3.6 Port discovery: CWD-relative, no liveness, no heartbeat **[CODE + HIST]**
- `PORT_FILE` is a bare relative path (`_tcp_bridge.py:31`) — resolves against the *client's* CWD (works today only because Claude launches at project root). The repo's own Go CLI does it right (`cli/internal/bridge/port.go` walks up to `.uproject`).
- Stale `port.txt` is trusted blindly (the 55558 incident: dead port re-read 4×, no fallback probe of 55557).
- C++ writes the port file once (`EpicUnrealMCPBridge.cpp:188`); a cook/package wiping `Saved/` mid-session orphans the still-listening bridge (bit us before — see memory `reference_mcp_bridge_port_recovery`).
**Fix:** resolve project root by walking up for `*.uproject` (or `UNREAL_MCP_PROJECT_DIR`); on connect-refused fall back to probing the default port; C++ re-asserts the port file on a slow tick.

### 3.7 `execute_python` comprehension scoping **[LIVE ×2 + CODE]**
`EpicUnrealMCPBridge.cpp:309-316` runs `exec(_code, _gl, _lc)` with split globals/locals — comprehensions and nested defs resolve free names via `_gl` and can't see top-level assignments (classic exec pitfall; hit twice this week as `NameError`). 
**Fix:** single namespace dict — `exec(_code, _ns)`; read `result` from `_ns`.

### 3.8 `take_screenshot` stale frame + no size control **[LIVE + CODE]**
`EpicUnrealMCPEditorCommands.cpp:1204` reads pixels without forcing a redraw — after python-side scene mutations we screenshotted the *old* scene until manually nudging the camera. No width/height params (viewport-size PNGs = image-token cost). `screenshot_widget` already does it right (double-draw + flush + clamp). 
**Fix:** `RedrawLevelEditingViewports(true)` + `FlushRenderingCommands()` before `ReadPixels`; optional target size (e.g. default max-width 1280 for verify loops).

### 3.9 Actor resolution inconsistency (incl. wrong world in PIE) **[LIVE + CODE]**
Label-or-name: `delete_actor`, `get/set_actor_property`, metadata. Name-only (label fails): `set_actor_transform:337`, `find_actors_by_name:141`, `apply_material_to_actor` (`BlueprintCommands.cpp:941` — bit us live), `set_mesh_material_color`, `spawn_actor` uniqueness. Param spelling varies (`name`/`actor_label`/`actor_name`). And `get_actors_in_level`, `find_actors_by_name`, `set_actor_transform` use `GWorld` → **operate on the PIE world during play**. 
**Fix:** one shared `ResolveActor()` (label | name | path, editor-world-context) used by every actor command; keep param aliases.

## 5. Feature gaps (verified absent) — ranked by leverage

1. **PIE control** — no play/stop/status/screenshot-in-PIE. The verify loop for anything runtime (the onboarding sky applies at BeginPlay!) currently requires a human in the headset/editor. `start_pie` / `stop_pie` / `pie_status` / screenshot-during-PIE would close the single biggest verification gap.
2. **Sequencer / Movie Render Queue** — zero tools. This is the **marketing-capture and VAD workhorse**: `Int_Spaceship` already has 9 authored CineCameras; MRQ automation = turntables, shot renders, device-quality capture for the Store submission *and* client deliverables in set-design work. Even a thin set (bind camera, set range, render MRQ job to disk) is high-value.
3. **Viewport framing** — every session we hand-roll atan2 math to aim the viewport. `frame_actor(actor, distance, angle)` / `look_at(location)` — trivial C++, big DX.
4. **Console command tool** — `execute_console_command` exists only via `execute_python` (two hops). One-liner tool.
5. **Contact sheet** — batch-screenshot N actors/cameras/angles into one labeled grid (client look-dev reviews; QA sweeps). Composable from existing pieces.
6. **Lighting build** — kick + poll Lightmass (set-design essential; Speakeasy's bake is done but freelance maps won't be).
7. **Editor lifecycle from the client** — `wait_until_ready` tool (pairs with the readiness gate); optionally `restart_editor` (relaunch script exists).
8. Longer-term: Landscape/foliage/PCG scatter (set dressing), USD/Datasmith import (VAD interchange), audio tools (zero today), animation/montage tools (zero today).

## 6. Portability kit (freelance set-design / VAD)

**Today:** plugin C++ is project-clean and drops into any UE 5.6 project; the Python venv + `.mcp.json` are what's fiddly. **Blockers:** `install.sh` installs from PyPI (may lag the local bridge) with no venv/cwd; port discovery is CWD-dependent (3.6); validator hardcoded to this machine.

**Target: "clone plugin → `./install.sh` → open editor → tools work" in <2 min on any project.**
1. `install.sh`: create `Plugins/UnrealMCP/.venv`, `pip install -e .`, write `.mcp.json` with absolute venv path **and `cwd` = project root** (also fixes 3.6 pending the real fix), print next steps.
2. Ship `launch-editor.sh` as a template (single-instance + port cleanup + boot-crash retry) parameterized by engine path.
3. Fix port discovery properly (walk-up to `.uproject`).
4. De-hardcode `validate_bridge.py`; wire it into CI as an optional live check.
5. README refresh (accurate counts, quickstart, known-limits page generated from the Notion tracker).
6. Optional: `UNREAL_MCP_TOOLS=<modules>` allowlist env to slim the 293-tool schema payload for focused sessions (harnesses without deferred loading pay it in full).

## 7. Skills / workflow layer (encode the playbooks)

Most of our hard-won know-how lives in session memory — invisible to other machines/projects. Convert into versioned **Claude Code skills** shipped in the plugin repo (`skills/`), so any project (and any collaborator) gets them:

- **`ue-verify`** — the screenshot loop done right: force redraw → screenshot (downscaled) → read → assert; PIE variant once PIE tools exist.
- **`ue-crash-triage`** — on bridge failure: check process/port/crash dir, extract assertion + callstack top, classify against the §2 signature table, recommend action (this audit's forensics, automated).
- **`ue-editor-lifecycle`** — launch/attach/wait-ready/restart conventions (wraps `launch-editor.sh`).
- **`ue-look-dev`** — the material/lighting iteration loop from the sky build (build graph → apply → verify → tune params), with the UMG/material gotchas baked in (from memories `reference_umg_via_unrealmcp`, `feedback_mcp_blueprint_limitations`).
